# mess-log fuzz targets (bn-gux)

`cargo-fuzz` (libFuzzer) targets for mess-log's untrusted-bytes decode
surfaces. This crate is deliberately its own `[workspace]` (see `Cargo.toml`)
so `libfuzzer-sys` and the nightly-only ASan build never leak into the main
workspace's stable build.

## Targets

- **`fuzz_scanner`** — `mess_log::scanner::scan_image(data, None)`. `data` is
  treated as a whole segment image (`SegmentHeader` + zero or more batches).
  Invariant asserted in-target: never panics; `safe_offset` and every
  accepted batch's span stay within `data.len()` (the A2 length cap bounds
  any single candidate, so this also bounds the walk's total work);
  accepted batches are contiguous with no gap/overlap/resync (A1/A10).
- **`fuzz_batch_decode`** — `mess_log::scanner::decode_batch(data, 0)`: the
  `BatchHeader` + `EventSubframe` decoder (magic/version/flags, the A2
  length cap, A3 marker echoes, the A4/A12 mandatory full-batch CRC, and the
  subframe-tiling pointer arithmetic). Invariant: never panics, no length
  arithmetic overflow, on any input.

Both entry points needed a `pub(crate)`/private → `pub` visibility bump in
`../src/scanner.rs` (`scan_image`, `decode_batch`, and the `Decoded` struct
`decode_batch` returns) to be reachable from this crate; see the doc comments
on each in `../src/scanner.rs` for why and exactly what changed. No behavior
changed — every widened item already had exactly the callers it has now,
just within the crate.

### Planned, blocked

`decode_cursor` (opaque client-supplied pagination cursor) and
`decode_ptr_block` (pointer-block / skip-table decoder) are **not yet
implemented anywhere in mess-log** — there is no decode entry point to fuzz.
Both are blocked on bn-25d. Add `fuzz_cursor_decode` /
`fuzz_ptr_block_decode` targets once those decoders exist, following the same
pattern as `fuzz_batch_decode` (byte-slice in, typed result out, assert only
"never panics" plus whatever structural invariant the decoder itself already
enforces).

## Running locally

```sh
# one-time (or whenever a richer seed set is wanted): regenerate the
# committed corpus from the real encoder/writer.
cargo run --release --bin gen_corpus

# a real campaign — 5+ minutes / 1M+ execs, whichever comes first:
cargo +nightly fuzz run fuzz_scanner -- -max_total_time=300
cargo +nightly fuzz run fuzz_batch_decode -- -max_total_time=300

# reproduce a crash file cargo-fuzz reports:
cargo +nightly fuzz run <target> artifacts/<target>/<crash-file>
```

CI (`.github/workflows/fuzz.yml`) runs both targets briefly (~2 min each) on
a nightly schedule with corpus caching across runs, seeded from the small
corpus committed under `corpus/`.

## Local run log (bn-gux)

Both targets were run for >= 5 minutes wall-clock (`-max_total_time=300`,
`-jobs=4 -workers=4`, i.e. 4 parallel libFuzzer workers each running the full
300s budget) against the seed corpus below, on `nightly-2026-04-29`:

- `fuzz_batch_decode`: 4 workers x ~167M execs = **~669M execs total**
  (worker exec counts: 167419256, 167768823, and two more in the same
  range), max RSS ~485 MiB/worker. `cov: 87 ft: 102`, corpus converged and
  stable well before the time budget ran out.
- `fuzz_scanner`: 4 workers x ~78-80M execs = **~314M execs total** (worker
  exec counts: 79545230, 78984349, 78677355, 77209450), max RSS ~523
  MiB/worker. `cov: 181 ft: 382`.

No crash, timeout, OOM, or leak was found in either run — both `artifacts/`
directories were empty at the end (`find artifacts -type f` = nothing). Both
targets ended clean at their time budget, several hundred times past the
1M-exec floor. The discovered corpus (34/210 additional inputs respectively)
was intentionally **not** committed — pruned back to the hand-picked seed set
above before committing, per the bn-gux protocol ("small seeds only").

## Corpus

`corpus/fuzz_scanner/` and `corpus/fuzz_batch_decode/` hold a small, hand-
picked seed set (clean single/multi-batch segments and batches built with
the real `SegmentWriter`/`BatchEncoder`, plus a few adversarial mutations:
torn tail, flipped CRC byte, huge `frame_count`/`compressed_len`, all-zero
header-sized buffer, empty file) — generated by `gen_corpus.rs`
(`cargo run --bin gen_corpus`), not hand-copied hex. Kept minimal per the
bn-gux protocol; libFuzzer's coverage-guided mutation is expected to grow
a much larger corpus locally/in CI, which is intentionally **not** committed.
